# Ritam UI release readiness design

The user authorized autonomous execution of the proposed catalogue, complete workflows, AI design guidance, accessibility evidence and open-source preparation. They are unavailable and asked for no questions. Preserve the approved design and settle reversible implementation details locally.

## Product boundary

Ship a reviewable React-web release candidate; keep the full long-term mobile/desktop/Figma ambitions in the master checklist. No invented production backend, accounts, payments or email delivery. Example data and async operations must say they are local demonstrations. Do not claim legal compliance, accessibility certification, proven superiority or improved AI taste without corresponding evidence.

## Architecture

Extend the existing installed-package reference app with a catalogue at `?view=catalogue` and three workflow routes at `?view=invoices`, `?view=settings` and `?view=onboarding`. Keep the existing workspace and composition comparison routes working. Catalogue metadata comes from the existing AI contract, with typed local preview implementations. Source and installation instructions remain useful before npm publication. Static assets contain the current contract and AI text. No new framework or UI dependency is needed.

Catalogue is a reading/exploration surface: compact brand header, clear installation and scope information, searchable categorized component navigation, focused preview/API/source area, foundations and workflow links. Use actual components; source excerpts must describe the displayed specimen. No decorative metric cards, huge marketing hero, invented endorsements or copied competitor assets.

Workflow routes share only a modest header and container, not an abstract application framework. Invoice records use a table and detail view; settings use grouped labelled forms; onboarding uses sequential steps and review. Use current library primitives, semantic markup and token CSS. Local state/storage errors must remain recoverable. Explicit async demo controls are acceptable to exercise failure paths. Preserve input when operations fail, guard duplicate submissions and restore meaningful focus.

## Release operations

Keep publication disabled until the owner grants the final license and registry credentials are available. Prepare an MIT proposal rather than silently granting irreversible rights. Add metadata, package-content checks, CI for normal builds/tests and browser verification, reproducible release documentation, contribution/security templates and third-party notices. Dependency checks report findings honestly rather than broadly upgrading the stack without evidence.

## Verification

Run existing unit/type/package/SSR/consumer/starter and story checks, plus catalogue search/no-results, route navigation, complete workflow success/failure/recovery and responsive/theme axe checks. Capture desktop/mobile light/dark and review actual images. Provide a fresh dated evidence record and separate manual accessibility gates. CI configuration is not evidence of a hosted CI run until it executes.

The release candidate is locally complete when implemented deliverables and automated checks pass with reviewed residual risks and no critical/important review findings. Public release remains gated on explicit licensing, registry/site settings and manual release evaluation.
